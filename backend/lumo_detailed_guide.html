Phase 1 — Environment & Contracts
Three-branch strategy
Create three long-lived branches: webapp for all Next.js/TypeScript UI code (lessons, quizzes, feedback UI, dashboard views), api for the FastAPI Planner service and agent microservices, and experiments for baseline reproductions and simulations of SOTA techniques like DKT.
Docker Compose services
A single docker-compose.yml brings up five services locally without any external dependencies: Next.js on port 3000, FastAPI on 8000, PostgreSQL on 5432, Redis on 6379, MinIO on 9000 (API) and 9001 (console). The workbook says the entire stack must run without external services — so all LLM calls should be mockable via environment flags at this stage.
Python + Node environment setup
Use uv (the Astral Python package manager) to manage the FastAPI and agent environments — it is faster than pip and produces a lockfile. Use npm for the webapp branch. Both environments must be fully reproducible from their lockfiles with no manual steps.
Gautam owns thisuv + npmDocker DesktopVSCode
Content schema
Holds lessons, quiz questions, feedback templates. Tables include: lessons (id, topic, grade_level, content_json, media_refs, curriculum_tag), quiz_questions (id, lesson_id, difficulty, correct_answer, distractors_json, misconception_type), feedback_templates (id, hint_level, tone, template_text).
Events schema
Tracks every user interaction. Tables: sessions (id, user_id, started_at, ended_at), user_events (id, session_id, event_type, payload_json, timestamp, response_latency_ms). This is the raw telemetry feed for the Attention Agent. Events include: lesson_started, question_answered, hint_requested, quiz_completed, break_taken.
Learner schema
Holds profiles and computed analytics. Tables: user_profiles (id, username, email, role, grade_level), mastery_scores (id, user_id, topic, score, updated_at), attention_metrics (id, user_id, session_id, focus_score, drift_flag, peak_window_start, peak_window_end).
Data retention function
The workbook specifies a 90-day retention policy. Write a PostgreSQL function that runs on a schedule, identifies user_events rows older than 90 days, strips user_id (replaces with a synthetic anonymized ID), and moves aggregated stats to a summary table. This must be built in this phase so the schema is designed to support it.
Team owns schemaNivedita owns telemetry tablesFERPA / COPPA compliant
Planner contract
The Planner is the only service the frontend calls. It must accept a LearningRequest (user_id, session_id, action_type, payload) and return a LearningResponse (action, content, rationale, next_suggested_action). The rationale field is mandatory in every response — this is how LUMO satisfies the transparency NFR.
Lesson Designer contract
Input: LessonRequest (topic, grade_level, learner_profile_id). Output: LessonContent (title, learning_objective, body_markdown, example_text, image_url, estimated_duration_mins). The JSON schema must be validated automatically — lessons that do not conform to schema are rejected before caching.
Quiz Agent contract
Input: QuizRequest (topic, learner_mastery_score, current_difficulty, n_questions). Output: QuizResponse (questions[], each with: question_text, options[], correct_index, misconception_type, difficulty_level, rationale). The misconception_type field is what triggers the Feedback Agent when a trap distractor is selected.
Feedback Agent contract
Input: HintRequest (question_id, learner_answer, hint_level_used, error_count, session_context). Output: HintResponse (hint_text, hint_level, sentiment_score, re_quiz_triggered: bool, nudge_text). Sentiment score must be validated — any output scoring below a threshold triggers fallback to scripted template.
Attention Agent contract
Input: streaming telemetry events from the events schema. Output: AttentionState (focus_score 0–1, drift_detected: bool, recommendation: enum[continue, micro_recap, break, easier_task], peak_window: bool). This is published to a Redis channel that the Planner subscribes to.

PII stripping middleware
Before any payload reaches the LLM, a FastAPI middleware must scrub: student name, email, phone, device fingerprint, and any biometric data. Replace with a synthetic learner ID (learner_#123 pattern). This is not optional — it is a hard COPPA requirement stated in the workbook.
Opt-in consent workflow
Advanced attention features (camera/mic for gaze or expression) require explicit parental opt-in. Build a consent flag in the user_profiles table (advanced_attention_consent: bool) and ensure the Attention Agent checks this before enabling any sensor-based inputs. Default is always off.
Telemetry event stubs
Nivedita must define the ingestion contract for events in this phase, even if real events are not flowing yet. Create stub endpoints that accept the event schema and write to a dev log — this lets other agents integrate against a real interface from Phase 2 onward.

Phase 2 — Baseline Reproduction
MDX for rich lesson content
Lessons are authored in MDX — a format that embeds interactive React components inside Markdown. This means a lesson can have a paragraph of text, then a drag-and-drop activity, then a visual, all in one file. The renderer must parse the LessonContent.body_markdown field as MDX and hydrate any interactive components.
Multi-format delivery (text / audio / drag-and-drop)
The workbook specifies three formats. Text is the default. Audio narration uses TTS — either on-device where possible, or a cloud TTS API as fallback with voices cached. Drag-and-drop activities are React components embedded in MDX. A format toggle in the UI lets students switch modes; the workbook says "no content mismatch between formats" — meaning all three formats must render the same learning objective.
WCAG accessibility
The workbook specifies WCAG compliance. Minimum requirements: all images have alt text, TTS is available for every text block, color contrast meets AA standard, and interactive elements are keyboard-navigable. Gautam owns this.
Storybook for component development
The workbook lists Storybook as a dev tool. Build each UI component (lesson card, quiz question, hint bubble, nudge banner) in isolation in Storybook before integrating into the app. This is especially important for child-friendly design — the workbook requires a usability test with children in Phase 6.
Gautam ownsNext.js + MDXStorybookWCAG AA
Session management
The Planner must create and manage sessions. On login, issue a JWT with a short lifetime. Each API call must include the JWT. The Planner validates it, loads the learner profile, and attaches session context to every downstream agent call. This is where RBAC is enforced — students, parents, teachers, and admins each see only what their role allows.
Goal decomposition
When a student selects a topic, the Planner decomposes the goal into: (1) fetch lesson, (2) deliver lesson, (3) serve quiz, (4) process answers, (5) apply feedback if needed, (6) update mastery. This sequence is the "learning loop" described throughout the workbook. The Planner orchestrates it by calling agents in order and passing state between them.
Transparency rationale injection
Every response from the Planner must include a human-readable rationale string explaining the adaptive decision that was made. Examples: "Difficulty raised because you answered 4 in a row correctly," "Break suggested because response times have increased over the last 3 questions." This rationale is displayed in the UI and logged.
Rate limiting + fallback logic
The Planner enforces rate limiting on all endpoints. If any downstream agent fails or is slow, the Planner must fall back to cached content rather than hanging. In Phase 2 this can be a simple in-memory cache; later phases use Redis.
Team ownsFastAPI + PydanticJWT (short lifetime)Redis fallback (later phases)
Static question bank
In Phase 2, the Quiz Agent uses a static bank of pre-authored questions stored in the quiz_questions table. No LLM yet. Questions are tagged by topic, grade, and difficulty (1–5). The agent selects questions matching the learner's current mastery level and difficulty tier.
Adaptive difficulty logic
This is the core algorithm defined in the workbook: if the learner scores ≥80% correct, raise difficulty by one tier for the next batch. If ≤40%, lower by one tier. Difficulty level and the reason for the change must be logged to the events schema for every quiz attempt. In this phase the logic is heuristic (threshold-based), not ML-based.
Summary chain quiz
The workbook specifies a "summary chain quiz" at the end of each unit — a quiz that covers the key steps of the unit in order, requiring ≥80% correct on all steps before the learner can advance to the next unit. This must be a distinct quiz mode in the agent, not just a regular quiz.
Celery for async quiz generation
Alshama uses Celery (with Redis as the broker) for async quiz generation. This matters in Phase 4 when LLM calls are involved and latency could interrupt the learning flow. Wire Celery in Phase 2 even if the tasks are synchronous stubs — it's harder to retrofit.
Alshama ownsFastAPI + CeleryStatic bank first, LLM in Phase 4
Single-level hint (Phase 2 scope)
In Phase 2, only a single scripted hint is needed — a light cue from the feedback_templates table. The full 3-tier ladder (light cue → guided step → worked example) is built in Phase 4. But the interface must be designed for 3 tiers from the start so no rework is needed.
Re-quiz trigger stub
The re-quiz trigger must be wired in Phase 2 as a stub. When the learner hits a wrong answer threshold, the Feedback Agent sends a re_quiz_triggered: true flag to the Planner. The Planner calls the Quiz Agent for a new question set on the same concept. In Phase 2 this can use the same static bank; in Phase 4 it uses LLM-generated questions.
Tone guardrail
Even at the stub level, all feedback output must have a positive, non-punitive tone. The workbook explicitly says "no punitive tone" and logs show reduced quit rate after nudges. In Phase 2, the guardrail is a simple word-list filter on template output. In Phase 4 it becomes a sentiment-score threshold on LLM output.

Event pipeline
Every agent emits events to the events schema via the telemetry endpoint. Nivedita owns this pipeline. In Phase 2, validate that events arrive, have correct timestamps, and have the right schema. Also verify temporal coherence — a lesson_started event must always precede a question_answered event in the same session.
Dashboard: mastery % and time per concept
The parent/teacher dashboard must show these two metrics from day one (they are listed as essential requirements). In Phase 2, these come from the mastery_scores table and aggregated session durations. The workbook says parents log in to see "accuracy %, time per concept, and strengths/weaknesses clearly" — the last one (strengths/weaknesses) can be stubbed as a placeholder in Phase 2 and filled in Phase 5.

Phase 3 — Vertical Workflow: Lesson → Quiz
Micro-lesson packs
Gautam prepares curriculum-aligned micro-lesson packs for the first demo topics (the workbook mentions fractions and addition as examples). Each lesson must be short (the workbook cites research on short focused lessons for retention), include at least one story or visual example, and align to a grade-level curriculum standard. Content is sourced from Open Educational Resources (OER) like CK-12 or OpenStax — the workbook specifically lists these to avoid licensing issues.
Lesson-to-quiz linking contract
Each lesson must be tagged with the quiz topics it unlocks. When a lesson is completed, the Planner passes the lesson's topic tag to the Quiz Agent as part of the QuizRequest. This ensures quiz questions are always about what was just taught.
Content tagging logic (misconception types)
Gautam also provides tagged content to the Quiz Agent — specifically, misconception types associated with each topic. For example, a lesson on fractions would tag common misconceptions like "treating numerator and denominator as independent whole numbers." These tags are used by the Quiz Agent to choose distractors in Phase 4.

Phase 4 — Closed Loop + Attention Hooks
Lesson Designer LLM integration
Gautam integrates Gemini for contextual explanations — specifically for when a student asks "why" or "how." The workbook calls these "contextual explanations in simpler words." The LLM call is: given lesson topic + learner grade + the question asked, generate a short age-appropriate explanation. The PII middleware from Phase 1 must intercept this call and strip learner identity before it goes to the API.
Age-appropriate safety filters
The workbook explicitly requires Gemini's safety filters to be configured for elementary-age content. Test with the red-team prompt set (built in Phase 6) to ensure no age-inappropriate content can be generated. The fallback when a safety filter triggers is cached curated content, not an error message.
Chain-of-thought prompting for hints
The workbook cites chain-of-thought prompting specifically for "targeted hints and explanations." Bhavya's hint generation prompts should instruct the LLM to reason step by step before producing the hint, so the hint reflects actual pedagogical reasoning rather than a surface-level response.
Gemini APICoT prompting for hintsAge-appropriate safety filtersPII middleware blocks before call
Tier 1: light cue
A brief nudge that points the student toward the right direction without giving anything away. Example: "Think about what happens when you share something equally." Scripted from feedback_templates. Available on the first wrong answer.
Tier 2: guided step
A more concrete breakdown of the problem-solving process. Generated by LLM using the question context and the specific misconception type. Example: "Let's break this down. First, how many parts are there in total?" The LLM prompt includes the question, the learner's wrong answer, and the tagged misconception.
Tier 3: worked example
The complete solution walkthrough. LLM-generated with chain-of-thought. Triggered only after the student has exhausted tiers 1 and 2. After a worked example, the system must auto-trigger a re-quiz on the same concept — the workbook says "hints lead to correct solution in ≤2 retries" and "mastery rate ≥80% after re-quiz."
Max 3 hints per question
The workbook specifies this as a hard limit. After tier 3, the system falls back to the worked example and triggers re-quiz. There is no tier 4. Bhavya must track hint_level_used in the session state and pass it with every HintRequest so the agent knows which tier to serve.
Bhavya ownsTier 1: scriptedTier 2–3: LLM + CoTMax 3 hints enforced
Misconception-based distractor generation
Alshama uses the LLM to generate "plausible but wrong" answers targeting known misconceptions. The LLM prompt includes: the question, the correct answer, the misconception type (from Gautam's content tags), and the grade level. The output is one or more distractors that a student with that misconception would plausibly select.
Distractor-to-feedback linkage
When a student selects a trap distractor, the quiz response must include the misconception_type that triggered it. The Planner passes this to the Feedback Agent, which uses it to generate a targeted explanation — not a generic "wrong answer" message but one that specifically addresses the misconception.
LLM summary chains
The workbook describes "summary chain quizzes" — a quiz that covers the core steps of a unit in sequence. Alshama implements LLM-assisted generation of these using the lesson's learning objectives as input. The LLM produces 3–5 questions testing each step of the concept in order.

Focus score computation
Nivedita builds the initial focus score from behavioral telemetry only (no camera/mic yet — those are optional features). The score is derived from: response latency (increasing latency = drifting focus), error rate over the last N questions, and idle time between events. These three signals combine into a focus_score between 0 and 1.
Drift detection — 60-second rule
The workbook specifies drift must be flagged within 1 minute. The Attention Agent must evaluate the focus score on every incoming event and publish a drift_detected: true alert to the Planner via Redis pub/sub if the score drops below threshold. The Planner then interrupts the current quiz and serves a micro-recap or lighter task.
Break suggestion + resume card
If an error streak is detected (the workbook mentions "error streak/slow times"), the Attention Agent recommends a break. The UI shows a break screen with a 1–2 minute timer and a resume card that accurately restores where the student was — topic, question number, current difficulty level. The workbook says "resume card accurate" as an acceptance criterion.
Peak time window detection
The Attention Agent tracks daily and weekly patterns. If a student consistently has high focus scores at 4pm, the agent records that as a peak window and advises the Planner to schedule harder topics during those windows. The workbook says "at least 1 peak window logged per day" as an acceptance criterion. The dashboard shows this as a "focus time heatmap."

Derived from mastery_scores across topics. Topics with scores ≥80% are strengths; below 60% are weaknesses needing support. The workbook lists this as an essential requirement for the dashboard. Display as a simple categorical list with progress bars.

Phase 6 — Verification & Validation
Four attack categories
The workbook defines four red-team categories: prompt injection (e.g. "ignore previous instructions" in the topic field), toxicity probing (requesting age-inappropriate content), privacy bait (asking the LLM to reveal other learners' data), and social engineering (pretending to be an admin to get elevated access).
Triage and labeling
Each red-team prompt is evaluated and labeled: Safe, Unsafe, or Ambiguous. Record the cause: which agent, which prompt, which tool call produced the unsafe output. This feeds the regression test suite — adversarial prompts that produced Unsafe outputs become golden test cases that run in CI.
Fallback on detection
The workbook specifies: prefix sanitizers (strip injection patterns from user inputs), deny-lists for known bad patterns, and automatic fallback to curated content when a safety filter trips. The fallback must be invisible to the student — they get a normal lesson, not an error.
Team owns4 attack categoriesGolden adversarial test cases in CIFallback = curated content, not error
Think-aloud with children (student interface)
The workbook specifies this methodology. Have children narrate what they are doing and thinking as they use the interface. Key metrics: ease of navigation, clarity of instructions, and emotional response (do they seem frustrated or engaged?). Also measure time-on-task and whether students follow break suggestions when shown.
SUS questionnaire (parent/teacher dashboard)
The System Usability Scale (SUS) is a standard 10-question survey scored 0–100. The workbook requires this specifically for the dashboard. The key scenario-based test question: "Can a teacher quickly identify the 3 students most likely to disengage?" If they can't do this in under 2 minutes, the dashboard needs work.

SLA targets (from workbook)
Planner: most requests <1s. Quiz Agent: <500ms. Feedback Agent (hints): <1.5s. Lesson Designer: <1s. Attention analytics: <1s. These are the contract SLAs — if any agent fails them, the Planner falls back to cache.
Load test: 30 concurrent students
Alshama and Nivedita run load tests simulating a classroom. Use Locust or k6 to simulate 30 concurrent students each going through the lesson → quiz → feedback loop. Measure p50, p95, p99 latency for each endpoint. Assert no session data bleeds across learners under concurrency.
LLM fallback rate
The workbook lists "LLM fallback rate" as a key metric. Under load, if the Gemini API is slow, the fallback rate will spike. Measure this and confirm that even at 100% fallback, the student experience is uninterrupted (cached lessons + static question bank).
